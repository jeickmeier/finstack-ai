FIXED (2026-08-20)  F-1  Environment/system HTTP proxy is inherited, and it
                bypasses the address pin.
  Fix: pinned_client (net-guard/src/client.rs) now calls .no_proxy() on
  the reqwest::Client builder, with a comment explaining that env/system
  proxies would receive the unpinned hostname, re-resolve it themselves,
  and bypass the .resolve() pin below, reopening the DNS-rebinding
  TOCTOU. The function's doc comment was updated to state proxies are
  disabled. Verified by inspection (the change is a single builder call)
  and by running the full existing suites for both crates
  (`cargo test -p finstack-ai-net-guard`, `cargo test -p
  finstack-ai-tools-fetch`) to confirm no regression. An automated test
  asserting a set HTTPS_PROXY is ignored was not added: both crates are
  #![forbid(unsafe_code)], and std::env::set_var is unsafe in this
  toolchain, so an env-var-based proxy test is not possible in-crate.
  Original finding text retained below for the record.

  --- original finding ---
  net-guard/src/client.rs:22-28 builds the client with
  reqwest::Client::builder() and never calls .no_proxy(). In
  reqwest 0.13.2 the builder default is auto_sys_proxy: true
  (async_impl/client.rs:305, 410-414), so HTTP_PROXY / HTTPS_PROXY /
  ALL_PROXY and platform proxy configuration are honored.

  Consequence: when a proxy is configured in the host environment,
  the connection target is the proxy, not the address returned by
  resolve_and_pin. The .resolve() override only steers direct
  connections, so:
    - the destination-name resolution is performed a second time, by
      the proxy, after net-guard vetted its own answer set. That is
      exactly the DNS-rebinding TOCTOU the pin exists to close
      (resolve.rs:79-105 docstring claims it is closed);
    - the proxy endpoint itself is never vetted, so egress can leave
      through a loopback or link-local address that
      is_forbidden_destination would have denied.
  TLS certificate validation still binds the far end to the
  allowlisted hostname on https, so this is a destination-vetting and
  egress-path bypass rather than a content-integrity break. Severity
  is Important, not Critical, because it requires proxy configuration
  in the host process environment (common in server deployments) and
  does not by itself let an attacker choose the proxy.

  Additionally, spec section 3 lists "proxy support" as an explicit
  v1 non-goal; the current code silently ships it as inherited
  default behaviour, so the shipped posture contradicts the spec.

  Suggested disposition (controller routes; not fixed here): call
  .no_proxy() in pinned_client, and add a test asserting the built
  client ignores a set HTTPS_PROXY. If proxied egress is later
  wanted, it must be an explicit config field whose proxy URL goes
  through the same vetting.

No Critical findings.

PASS  URL parse and component policy (TM-22, SEC-INV-007)
      vet.rs:51-82. Parse via the url crate; scheme restricted to
      https, or http only when policy.allow_loopback_http AND the
      host is loopback (vet.rs:70); userinfo (username or password)
      rejected (vet.rs:59); fragment rejected (vet.rs:63); missing
      host and missing port rejected; https confined to port 443
      (vet.rs:73). Non-http(s) schemes (file:, data:, gopher:, ftp:,
      jar:) fall out at vet.rs:56. IPv6 forms are handled by
      stripping the parser's brackets before IpAddr::parse
      (vet.rs:38-41, resolve.rs:84), and to_canonical() collapses
      IPv4-mapped ::ffff:127.0.0.1 shapes before the deny test
      (resolve.rs:43, 63). IDNA: hosts arrive punycoded and
      lowercased from the parser and allowlist entries are compared
      in that form (tests.rs:57 unicode_hosts_normalize_to_punycode);
      a Unicode allowlist entry therefore cannot match a punycode
      host, which fails closed (see F-5).
      Residual: none material. Note that the https-port-443-only rule
      makes allowlisted hosts on non-standard TLS ports unusable;
      that is a deliberate conservative choice, not a gap.

PASS  Destination deny set (TM-22)
      resolve.rs:42-60. Denied after canonicalization: IPv4 loopback,
      private (RFC1918), link-local (169.254/16, which covers the
      cloud metadata endpoint), unspecified (0.0.0.0), broadcast, and
      multicast; IPv6 loopback, unique-local (fc00::/7),
      unicast-link-local (fe80::/10), unspecified, and multicast.
      This is a superset of the spec's draft list — unspecified,
      broadcast, and multicast were added beyond spec section 5 text,
      which is why the proposed TM-22 row names them.
      Residual: IPv4 shared address space 100.64.0.0/10 (CGNAT) and
      benchmarking 198.18.0.0/15 are not denied, and IPv6
      documentation/ORCHID ranges are not denied. Reaching them still
      requires an allowlisted hostname that resolves there, so the
      allowlist remains the binding control. Accepted.

PASS  DNS rebinding TOCTOU (TM-22, resolve-and-pin)
      resolve.rs:79-105 vets EVERY address in the answer set and
      returns DestinationBlocked if any one is forbidden
      (resolve.rs:97-99), then pins the first address; client.rs:26
      installs it as a DNS override so the socket connect cannot
      re-resolve. Literal-IP hosts skip resolution but not the deny
      check (resolve.rs:85-90). A fresh client is built per hop
      (pipeline.rs:249), which is required for correctness and must
      not be "optimized" into a shared client. Evidence:
      net-guard tests one_private_address_rejects_the_whole_set
      (tests.rs:94), first_public_address_is_pinned (tests.rs:109),
      literal_hosts_skip_resolution_but_not_the_deny_check
      (tests.rs:122), empty_resolution_fails (tests.rs:134); fetch
      tests pinned_address_overrides_dns_for_hostnames
      (tests.rs:1119).
      Residual: voided by F-1 in a proxied environment. Also, the
      pin is per-hostname and port-agnostic by design (reqwest
      ignores the port in a resolve override and uses the URL's
      port); since the URL port is itself vetted, this is safe.

PASS  Redirect attack surface (TM-22)
      pipeline.rs:344-369. Client-level redirect following is
      disabled (client.rs:25) and the loop is manual. Only
      301/302/303/307/308 are treated as redirects
      (pipeline.rs:352); every other non-2xx becomes a terminal
      transport error, so exotic 3xx (300, 304, 305 "use proxy",
      306) cannot be followed. next_hop (pipeline.rs:290-304)
      resolves Location with url::Url::join against the current URL,
      so relative and protocol-relative ("//evil.example") Locations
      are resolved rather than mis-parsed, and the result is then
      re-vetted through the full parse_and_vet_url + allowlist +
      resolve_and_pin path, i.e. spec section 4.4 step 7 is honoured.
      Downgrade: an https origin redirected to http fails
      plaintext_http_forbidden at vet.rs:70-72 because the hop is not
      loopback. Loopback steering: origin_is_loopback is computed
      once from hop 0 (pipeline.rs:330) and threaded into
      host_allowed (pipeline.rs:159-169), so a compromised
      allowlisted public host cannot 302 the chain into
      http://127.0.0.1:<port>/. Hop cap enforced at
      pipeline.rs:353 with max_redirects <= 5 by config ceiling
      (config.rs:26, 228). Evidence: tests.rs:824, 850, 877, 902.

      TEST GAP CLOSED (2026-08-20): the redirect tests above covered
      cross-host-to-unlisted-host denial and same-host follows, but not
      an allowlisted redirect target that resolves to a private
      address — the case that specifically exercises the hop-N
      resolve_and_pin re-vet rather than the allowlist check alone.
      Added redirect_to_allowlisted_host_resolving_private_is_blocked
      (tests.rs): a loopback origin fixture 302s to
      https://internal.example/x, which IS on the allowlist; the
      scripted resolver answers 10.0.0.1 for it; asserts
      FETCH_DESTINATION_BLOCKED. Passes.

PASS  Header and credential isolation (TM-04, TM-22)
      Per-host headers are looked up by the current hop's exact host
      (pipeline.rs:254) against keys that config::validate has
      normalized to lowercase and required to be exact (non-wildcard)
      hosts (config.rs:236-251). A credential configured for host A
      is therefore never emitted on a hop to host B; a same-host
      redirect keeps it, which is intended. Values are re-validated
      as HTTP header values at construction and again per send.
      HttpFetchConfig's Debug renders every header value as
      "<redacted>" (config.rs:31, 140-163) and HttpFetchToolset's
      Debug prints only the pattern count and store presence
      (toolset.rs:163-171). No header value appears in any error
      string. Evidence: tests.rs:204 debug_redacts_per_host_headers,
      tests.rs:740, tests.rs:933 headers_do_not_cross_hosts_on_redirect.

PASS  Response handling and bounds (SEC-INV-007, TM-16)
      client.rs:38-52 streams the body and returns LimitExceeded the
      moment the accumulated length would exceed the cap — an error,
      never a silent truncation, and the overflow check uses
      saturating_add. The effective cap is
      min(config.max_response_bytes, args.max_bytes)
      (pipeline.rs:377-380) and the same number bounds the inline
      result after decoding/markdown conversion
      (deliver.rs:193-202, markdown.rs:32), so a lossy-UTF-8
      expansion cannot smuggle a larger string into the transcript
      (tests.rs:662). Config ceilings are construction errors, not
      clamps: 8 MiB bytes, 120 s timeout, 5 redirects
      (config.rs:17-28, 218-232; tests.rs:152). reqwest is built with
      default-features = false and no gzip/brotli/deflate feature, so
      no automatic decompression happens and the cap is a wire-byte
      cap — decompression bombs are not reachable through this path.

PASS  Error surface (TM-04)
      All net-guard error variants carry &'static str reasons only
      (lib.rs:33-60), and the pipeline maps them to fixed strings
      (pipeline.rs:111-144). No URL, header, body, or address value
      is interpolated into an error message except the bounded
      endpoint-rejection detail covered by F-2 below. Error codes are
      the frozen FETCH_* vocabulary (lib.rs:41-53).

PASS  Artifact staging and tenant scoping (TM-20, SEC-INV-008)
      deliver.rs:153-190 stages through stage_required_artifact with
      an ArtifactScope built from ctx.run.locator (tenant_scope,
      session_id, run_id) and Sensitivity::Internal — the same call
      shape as finstack-ai-tools-openrouter-media. No caller-supplied
      field participates in the scope, so a model cannot address
      another tenant's store. toolset.rs:237-250 additionally rejects
      a call whose authenticated principal's tenant scope differs
      from the committed effect's locator scope. With no store
      attached, binary/oversize bodies fail closed with
      fetch_limit_exceeded rather than being inlined
      (deliver.rs:37-43, 143-145; tests.rs:535).

PASS  Fail-closed configuration and default-graph posture
      (SEC-INV-012, section 15 gate)
      config::validate rejects an empty allowlist first
      (config.rs:207-211); HostPattern::parse rejects entries
      containing '*', '/', ':', '?', '#', '@', or whitespace after an
      optional "*." prefix and rejects empty labels
      (config.rs:56-75), so a bare "*" is rejected and scheme, port,
      path, or userinfo cannot be smuggled into an allowlist entry.
      Bare-TLD wildcards such as "*.com" are still accepted (see F-6). Wildcard matching
      requires a non-empty proper subdomain label, so
      "*.wikipedia.org" does not match "wikipedia.org" or
      "notwikipedia.org" (config.rs:88-93; tests.rs:180). Both crates
      are separate opt-in packages with default = [] features; no
      default SDK feature pulls them in. Evidence: tests.rs:147
      empty_allowlist_refuses_to_construct.

PASS  Spec section 4.4 ordering
      The implementation orders parse/vet (pipeline.rs:327) before
      the allowlist match (pipeline.rs:238), where the spec lists
      allowlist as step 2 and vetting as step 3. This inversion is
      necessary — the allowlist matches on the parsed host — and is
      security-neutral: both run before any socket connect, the
      cancellation/deadline gate still precedes both
      (pipeline.rs:346), and each redirect hop re-enters at the
      allowlist check. Recommend the spec text be corrected rather
      than the code.

  non_success_status_reports_bounded_detail (tests.rs) now asserts the

  bounding/redaction assertions.
  NOT closed: channel (b), the success-content "content" field
  (pipeline.rs), remains unwrapped per the spec's content contract —
  ordinary tool output, not error text, so wrapping it would violate the
  documented success-path shape. This is recorded as a framework-level
  follow-up: if/when ToolResult gains a provenance/sensitivity channel
  (as the original finding recommended), this toolset should be an early
  adopter for the success path. Original finding text retained below for
  the record.

  --- original finding ---
  Untrusted response bytes reach the model context with no
            provenance marking.
  Two channels. (a) On a non-2xx terminal status, up to 4096 bytes of
  the endpoint's body are read and up to 300 characters are
  whitespace-collapsed into the ToolError message
  (pipeline.rs:29-32, 172-208). (b) On success, the fetched body (or
  its Markdown rendering) is placed in the result JSON's "content"
  field (pipeline.rs:406-412) as ordinary tool output.
  Both are bounded, which is what SEC-INV-007 requires, and TM-01's
  "treat content as data" is a framework-level property of tool
  results rather than something this toolset can assert. But note the
  contrast with finstack-ai-context-repository, which marks retrieved
  file content QuotedSource + Untrusted + external:true. Fetched web
  pages are strictly more hostile than repository files and currently
  carry no equivalent marking, and channel (a) puts attacker-chosen
  prose into an *error* message, where a reader is least likely to
  expect adversarial content. Recommendation (follow-up, not a
  blocker): if ToolResult gains a provenance/sensitivity channel,
  this toolset should be an early adopter; meanwhile consider
  prefixing the rejection detail with an explicit "remote endpoint
  said:" delimiter.

MINOR  F-3  Time is bounded per hop, not per call.
  request_timeout is a reqwest total timeout and does cover the body
  stream (reqwest 0.13.2 async_impl/response.rs:39-45), so no hop can
  hang. But the cap is applied per hop, so a chain of
  max_redirects + 1 hops can consume up to 6 x 120 s of wall clock
  when the run carries no deadline. Separately, the
  cancellation/deadline select! wraps only request.send()
  (pipeline.rs:274-283); the body read (client.rs:38) and the
  rejection-detail read (pipeline.rs:172) are not raced against
  ctx.run.cancellation, so a cancelled run keeps a trickling body
  alive until the per-hop timeout fires. Both are bounded, so this is
  a responsiveness/resource-fairness issue rather than an unbounded
  one. Deployments that need a hard ceiling should set a run deadline
  — which IS honoured between hops (pipeline.rs:346).

FIXED (2026-08-20)  F-4  Adversarial HTML nesting depth is untested against
                the htmd/html5ever conversion path.
  Confirmed the concern first: a test generating a 100,000-level-deep
  `<div>` document and calling html_to_markdown, run in isolation
  (`cargo test -p finstack-ai-tools-fetch deeply_nested_html_does_not_crash
  -- --nocapture`), reproduced the abort exactly as predicted — thread
  overflowed its stack, SIGABRT, process aborted with exit signal 6
  (not a returned error).
  Fix: markdown.rs now runs exceeds_safe_nesting_depth, a single-pass
  byte scan, before handing input to htmd/html5ever. It counts `<`
  followed by an ASCII letter as depth += 1 and `</` as
  depth.saturating_sub(1), with no tag-name tracking (so a run of
  sibling void elements like consecutive <br> tags over-counts, which
  can only make the guard reject more than strictly necessary, never
  fewer). MAX_SCAN_DEPTH = 512, documented on the constant and in
  html_to_markdown's doc comment. Over-cap returns None, same fallback
  path already used for conversion failure and output-cap overflow, so
  the caller falls back to its already-budget-checked inline-text path
  rather than the whole fetch erroring.
  Tests (markdown.rs): deeply_nested_html_does_not_crash (100,000
  levels; asserts None — the guard trips) and
  moderately_nested_html_still_converts (100 levels, well under the
  512 cap; asserts Some and that the converted text is present), plus
  the existing goldens/pathological-markup tests as regression
  coverage. `cargo test -p finstack-ai-tools-fetch` (51 tests) and
  `cargo clippy -p finstack-ai-tools-fetch --all-targets` both pass
  clean after the change.

  UPDATE (2026-08-20, review pass): the initial guard above (a bare
  integer counter, `depth += 1` on any `<tag`, `depth -= 1` on any
  `</`) was found to be BYPASSABLE. html5ever ignores an end tag with
  no matching open element on its stack of open elements, so it does
  NOT treat a mismatched close as a decrement. A document built from
  100,000 repetitions of `<div></span>` therefore kept the naive
  counter near depth 0-1 (each `</span>` decremented it right back
  down) while html5ever's real DOM nested 100,000 unclosed `<div>`s —
  the stack-exhaustion abort this guard exists to prevent stayed fully
  reachable. Reviewer compiled the guard directly and confirmed
  `exceeds_safe_nesting_depth` returned `false` for that input.
  Fix (this pass): replaced the bare counter with a bounded stack of
  lowercased open tag names. A closing tag now pops the stack ONLY
  when its name equals the top of the stack; a mismatched or stray
  close is ignored (no pop), mirroring html5ever's ignore-unmatched
  behavior in the conservative direction. Void elements (`br`, `img`,
  `input`, etc.) and explicit self-closing tags (`<x/>`) are recognized
  and never pushed. The cap trips the moment the stack itself would
  exceed `MAX_SCAN_DEPTH` (512), so mismatched-close padding now GROWS
  the tracked depth and trips the guard instead of masking it. The
  "can only reject more documents than strictly necessary, never
  fewer" claim in the doc comment now actually holds, with the
  ignore-mismatched-closes rule stated as the reason, plus a
  documented residual: implied-close patterns html5ever's
  tree-construction algorithm handles specially (huge sibling `<li>`
  runs, misnesting like `<b><i></b>`) are not modeled, so those could
  in principle false-positive at extreme scale — accepted, since the
  failure mode is a fallback to inline text, not an error or a crash.
  New regression test `mismatched_close_padding_does_not_bypass_the_depth_guard`
  (markdown.rs): 100,000 repetitions of `<div></span>` asserts `None`
  (guard trips) and does not crash. All pre-existing depth-guard tests
  (deeply_nested_html_does_not_crash, moderately_nested_html_still_converts)
  and the full suite still pass; `cargo test -p finstack-ai-tools-fetch`
  (54 tests at this point, other agents' work included) and
  `cargo clippy -p finstack-ai-tools-fetch --all-targets` both clean.

  UPDATE 2 (2026-08-20, second review pass): the stack-based fix above
  introduced its OWN critical bypass, also found and confirmed by the
  reviewer with a real SIGABRT reproduction. The guard's opening-tag
  handling treated any trailing `/` (`<div/>`) as self-closing and
  skipped the push, on the assumption that a self-closed tag cannot
  stay open. That assumption is wrong for ordinary HTML elements: per
  the HTML5 tree-construction algorithm, a self-closing slash is only
  honored on void elements and on foreign-content (SVG/MathML)
  elements — on a plain element like `<div/>` it is IGNORED and the
  element stays open exactly as `<div>` would. `"<div/>".repeat(100_000)`
  therefore pushed nothing under the old rule (the guard reported "not
  exceeded") while html5ever built a real DOM ~100,000 elements deep,
  reproducing the same SIGABRT stack-overflow abort this guard exists
  to prevent — and more easily than the first bypass, since it needs
  only one repeated fragment rather than a padding trick. Reviewer
  confirmed `real_dom_depth("<div/>" x 1000) == 1002` while the guard
  returned `false`.
  Fix (this pass): dropped `self_closing` from the push condition
  entirely (and removed the now-dead variable/detection code). A tag
  is now pushed onto the stack unless it is a [`VOID_ELEMENTS`] entry,
  full stop — a trailing `/` no longer matters for non-void elements.
  `<div/>` and friends now count as opens, matching html5ever. Accepted
  new residual, added to the doc comment's list alongside the
  implied-close/`<li>` case: genuine foreign-content self-closing
  elements (SVG/MathML, e.g. `<path/>`, `<circle/>`), which html5ever
  DOES honor as self-closing, are over-counted by this
  namespace-unaware scan, so an SVG-heavy document with more than
  `MAX_SCAN_DEPTH` (512) such elements will fall back to plain text
  even though html5ever would have handled it fine. Fail-closed and
  accepted, same as the other residual.
  New regression test `self_closing_non_void_padding_does_not_bypass_the_depth_guard`
  (markdown.rs): `"<div/>".repeat(100_000)` asserts `None` (guard
  trips) and does not crash. All prior depth-guard tests
  (deeply_nested_html_does_not_crash, moderately_nested_html_still_converts,
  mismatched_close_padding_does_not_bypass_the_depth_guard) still pass.
  `cargo test -p finstack-ai-tools-fetch` (57 tests at this point,
  other agents' work included) and
  `cargo clippy -p finstack-ai-tools-fetch --all-targets` both clean.
  Original finding text retained below for the record.

  --- original finding ---
  Adversarial HTML nesting depth is untested against the
            htmd/html5ever conversion path.
  markdown.rs:24-36 hands up to max_response_bytes (default 2 MiB,
  ceiling 8 MiB) of attacker-controlled markup to htmd 0.5 /
  html5ever. Memory safety is not the concern — the crates are safe
  Rust and both this crate and net-guard are #![forbid(unsafe_code)]
  — but a document of ~hundreds of thousands of nested elements can
  drive a recursive tree walk (and recursive Drop of the resulting
  tree) into stack exhaustion, which aborts the process rather than
  returning an error. fixtures/pathological.html (127 bytes) covers
  malformed/unclosed markup only, not depth; the README is explicit
  that no fixture makes conversion fail. Not demonstrated here, and
  the blast radius is availability of the host process for an
  allowlisted-host fetch. Recommended follow-up: a generated
  deep-nesting fixture (for example 100k nested <div>) exercised in
  a test, and, if it does blow the stack, a pre-conversion depth or
  tag-count guard.
  Dependency surface note for the register: htmd 0.5 (MIT, cleared by
  cargo deny check licenses per the crate README) pulls html5ever /
  markup5ever / tendril, which do contain unsafe internally. This is
  the feature's largest new untrusted-input parser and belongs on the
  TM-18 / TM-16 radar for advisory watch.

ADDENDUM (2026-08-20) — code-review follow-up pass
================================================================

Four further findings from a code-review pass over the committed
candidate were fixed in the same pass as F-5 above (see CLOSED F-5
above; not repeated here):

1. Loopback scope was the whole 127.0.0.0/8, not the exact address.
   vet.rs's is_loopback_host and resolve.rs's blocked() both used
   IpAddr::is_loopback(), which accepts every address in 127.0.0.0/8 for
   IPv4. Under allow_loopback_http, that meant a hostname resolving to
   e.g. 127.77.1.2 (never a real loopback binding, but still inside the
   /8) would have been treated as loopback and let through the
   allowlist bypass. Narrowed both call sites to the exact conventional
   addresses only: `localhost`, `127.0.0.1`, and `::1` (accepting the
   IPv4-mapped `::ffff:127.0.0.1` form via to_canonical() comparison
   against Ipv4Addr::LOCALHOST/Ipv6Addr::LOCALHOST). Note this is scoped
   to the ALLOW carve-out only — the DENY set (is_forbidden_destination)
   deliberately still treats the whole 127.0.0.0/8 as loopback-and-thus-
   forbidden by default; only the exception that lets fixtures through
   was narrowed. New tests: net-guard's
   loopback_scope_is_exact_not_whole_127_8 (vet.rs level) and
   resolved_address_in_127_8_but_not_exact_loopback_is_still_blocked
   (resolve_and_pin level, via a scripted resolver answering
   127.77.1.2 for a "localhost" lookup). `cargo test -p
   finstack-ai-net-guard -p finstack-ai-tools-fetch` passes (both
   crates re-run per the note in the original F-4/loopback finding
   that net-guard changes must be verified against both suites).

2. allow_loopback_http was reachable from config data, not just code.
   HttpFetchConfigSnapshot::from_json (config.rs) accepted an
   "allow_loopback_http" JSON key and applied it directly, so the
   single largest privilege this crate can grant (see the field's own
   doc, F-7 above) could arrive embedded in a config file, database
   row, or any other data path that eventually calls from_json — not
   only from a reviewed call site. Removed the field from
   HttpFetchConfigSnapshot entirely; with #[serde(deny_unknown_fields)]
   already on the type, a JSON document that still carries the old key
   now fails to parse rather than being silently honored or ignored.
   HttpFetchConfig::allow_loopback_http itself is unchanged (still a
   plain bool, still settable when a caller builds the struct directly
   in Rust) — its doc now says explicitly it is not settable via the
   JSON snapshot by design. The Python binding (which is the one
   from_json caller that legitimately needs the fixture bypass) gained
   a keyword-only constructor argument, insecure_allow_loopback_http:
   bool = False, applied to the parsed config AFTER from_json returns —
   i.e. in Rust code in fetch.rs, never read from the JSON payload. The
   .pyi stub and class docstring were updated to match; the Python e2e
   test that previously passed "allow_loopback_http": true in the JSON
   now passes insecure_allow_loopback_http=True as the constructor
   argument instead, and a new test asserts JSON still carrying the old
   field is rejected. New Rust tests: snapshot_from_json_honors_every_field
   was adjusted (no longer includes the field in its input JSON, asserts
   the output is always the code default) and
   snapshot_from_json_rejects_allow_loopback_http_field was added.

3. ArtifactError::TooLarge was collapsed into the generic transport
   failure. deliver.rs's stage_artifact mapped every ArtifactError
   variant from stage_required_artifact through one blanket map_err to
   FETCH_TRANSPORT_FAILED / ErrorCategory::Tool, so a body too large for
   the attached artifact store's own byte ceiling was indistinguishable
   from a genuine staging fault (I/O error, integrity failure, etc.) —
   both surfaced identically. Replaced the blanket map with a match:
   ArtifactError::TooLarge{..} now maps to FETCH_LIMIT_EXCEEDED /
   ErrorCategory::Limit ("fetch content exceeds the artifact store's
   byte limit"), a limit condition the caller can act on; every other
   variant keeps the prior FETCH_TRANSPORT_FAILED / ErrorCategory::Tool
   mapping. New test artifact_store_too_large_maps_to_fetch_limit_exceeded
   (tests.rs) uses InProcessArtifactStore::default().with_max_artifact_bytes(2)
   and a small binary body to force TooLarge, and asserts the mapped
   code and message.

4. The toolset's configurable result ceiling could exceed the kernel's
   fixed RawJson ceiling. toolset.rs's result_ceiling computed
   max_response_bytes + RESULT_ENVELOPE_BYTES with no upper bound, so a
   deployment configuring max_response_bytes near its 8 MiB hard ceiling
   would advertise (and enforce, in call()'s own over-ceiling check) a
   max_result_bytes well above the 1 MiB that
   finstack_ai_kernel::RAW_JSON_MAX_BYTES actually allows RawJson::parse
   to accept. A serialized result between 1 MiB and the toolset's own
   ceiling would therefore pass call()'s check only to fail inside
   RawJson::parse immediately afterward, with a generic/internal error
   instead of the crate's stable FETCH_LIMIT_EXCEEDED. Fixed by clamping
   result_ceiling's output to min(max_response_bytes + 4096,
   RAW_JSON_MAX_BYTES) (the kernel constant, which is publicly
   re-exported from finstack_ai_kernel and imported directly rather than
   duplicated). This makes the toolset's own over-ceiling check in
   call() fire first, before RawJson::parse ever runs, for any
   serialized output past 1 MiB — with the toolset's own error code, not
   the kernel's. config.rs's max_response_bytes doc now states inline
   results are additionally bounded by this 1 MiB ceiling regardless of
   the configured value, and that bodies needing to exceed it require an
   artifact store (unaffected, since staged artifact refs are tiny).
   ToolSpec::validate() still passes (max_result_bytes is simply
   smaller, never larger, than before). New test
   inline_result_over_the_kernel_raw_json_ceiling_is_a_limit_error
   (tests.rs): max_response_bytes configured to 2 MiB, a fixture serving
   ~1.2 MiB of ASCII text, no artifact store, mode auto — asserts
   FETCH_LIMIT_EXCEEDED (not FETCH_INVALID_ARGUMENTS).

Also documentation-only: net-guard's client.rs (pinned_client doc) and
README.md now carry an explicit "Redirect loops" note: because redirect
following is disabled and the caller owns the hop loop, every hop —
not just hop 0 — must re-run the full parse-and-vet → allowlist →
resolve-and-pin sequence, and any loopback/fixture bypass must be
decided once from the original (hop-0) URL and never recomputed per
hop, referencing finstack-ai-tools-fetch's host_allowed/
origin_is_loopback (pipeline.rs) as the reference implementation this
crate's own consumer already follows correctly. No behavior changed;
this closes a documentation gap on an invariant the code already
upheld (see the "Redirect attack surface" area verdict above,
Loopback steering paragraph).
